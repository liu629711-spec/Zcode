# Agent 项目空间：目标与边界

## 目标

工程模式把一个持续推进的工程目标组织成一个用户可操作的项目空间：用户从想法开始，经过澄清、方案、任务、执行、验证和验收，最终得到可追溯的交付结果。

这里的“项目”不是一次聊天、一个 session 或一个 workflow run。它是一个面向用户的顶层上下文，关联这些已有事实：

```text
项目目标
  → 阶段和工作项
  → Agent session / workflow run
  → 文件改动、Git checkpoint 和产物
  → 验证结果与交付决定
```

项目空间保存关联和用户决定；具体 Agent 执行仍由现有 runtime、Task、Dynamic Workflow、Expert Workflow、Host 和 journal 负责。

## 三个核心承诺

### 能看见

用户能看到：

- 项目要解决什么问题；
- 当前处于哪个阶段；
- 哪些工作项已完成、执行中、等待依赖、等待用户、失败或受阻；
- 每个工作项由谁执行、产生了哪些改动和产物；
- 已运行哪些验证，哪些结论仍未确认。

展示用户语言的阶段和工作项，不要求用户理解 actor、node、run 等内部术语。

### 能干预

用户可以在项目过程中：

- 补充背景或新增约束；
- 修改尚未开始的工作项；
- 回答 Agent 的问题或权限请求；
- 暂停、恢复或停止项目；
- 重试失败工作项；
- 在交付前要求重新验证或提出修改意见。

追加背景、修改计划、停止项目、停止单个工作项、重试和重新规划必须是不同动作，不能用一个“继续”按钮混合表达。

### 能验收

项目运行结束不代表项目已交付。交付前必须能核对：

- 目标是否覆盖；
- 声明的文件或产物是否真实存在；
- 验证命令和检查是否实际执行；
- 关键结论是否有依据；
- 未确认项、冲突和失败是否披露；
- 用户是否已经接受当前结果。

## 生命周期

```text
draft
  → clarifying
  → planned
  → approved
  → executing
  → verifying
  → awaiting_acceptance
  → delivered
```

`blocked`、`partially_delivered`、`cancelled` 和 `failed` 是可以从执行或验证阶段进入的异常结果。它们不能被折叠成普通的“完成”。

需要分开记录四类事实：

- **执行事实**：Agent、节点和 run 是否仍在运行、等待、失败或停止；
- **流程事实**：依赖是否满足、后续工作是否还能继续；
- **结果事实**：当前阶段得到成功、部分完成、暂停还是错误；
- **交付事实**：结果是否完整、可验证并被用户接受。

## 简单任务边界

以下请求保持普通聊天或普通 Agent 路径：

- 回答一个明确问题；
- 修改一个小地方；
- 执行一次简单命令；
- 不需要持续上下文或验收的短任务。

以下情况适合进入工程模式：

- 目标需要多阶段推进；
- 需要先澄清范围或形成方案；
- 涉及多个文件、模块或接口；
- 需要多个工作项协作或有依赖关系；
- 需要测试、预览、代码审查或用户验收；
- 用户希望持续观察和反复干预。

## 用户确认点

工程模式不要求用户理解脚本和调度器，但在高影响节点保留可理解的确认：

1. **范围确认**：项目要做什么、不做什么，以及如何判断完成；
2. **方案确认**：架构、接口、任务计划和主要风险；
3. **执行确认**：允许开始修改文件、运行高影响操作或创建提交；
4. **交付确认**：用户查看结果、证据和未完成项后接受或要求修改。

删除文件、安装依赖、提交、推送、发布和其他外部副作用仍遵守现有权限和平台边界。

## 设计边界

- 不新建第二套 Agent 调度器、后台队列、事件系统或运行时 journal。
- 不把每个普通请求强制升级为项目。
- 不把 workflow 脚本作为普通用户的必需知识。
- 不把 UI 状态当作业务事实；事实必须来自既有 runtime、journal 和服务投影。
- 不把 Agent 自述完成当作验证证据。
- 不把 `run completed` 直接显示为 `delivered`。
- 第一阶段只定义单 workspace 内的项目闭环，不提前承诺多仓库、自动发布或无人值守交付。

## 本 spec 的作用

本文件只确定产品目标、用户规则和边界，不提前决定数据库表、协议字段、组件结构或具体实现顺序。后续行为改动必须分别补充领域模型、状态事件、干预协议、交付验收和端到端场景 spec。
