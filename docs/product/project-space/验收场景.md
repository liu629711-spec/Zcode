# Agent 项目空间：验收场景

这些场景用于后续设计、实现和端到端测试。每个场景都要同时检查用户看到的状态、可执行的操作和最终事实，不能只看代码或单个 Agent 是否返回成功。

## S1：从想法建立项目

**输入**：用户只有一句模糊想法，例如“我想做一个帮助小团队管理知识的工具”。

**期望**：

- 系统先帮助澄清目标、使用对象、范围和限制；
- 形成用户能读懂的项目简报；
- 提出可确认的验收标准；
- 用户确认前不开始高影响的代码修改；
- 项目上下文可以回看和继续。

## S2：形成方案和任务计划

**输入**：用户确认项目简报。

**期望**：

- 系统给出架构方向、接口/模块边界和主要风险；
- 将方案拆成有依赖关系的工作项；
- 明确哪些工作可以并行，哪些工作必须等待；
- 用户可以修改范围或任务计划；
- 用户确认后才进入执行阶段。

## S3：执行过程可见

**输入**：用户批准任务计划并开始执行。

**期望**：

- 用户看到当前阶段和总体状态；
- 每个工作项显示待开始、执行中、等待依赖、等待用户、已完成、失败或受阻；
- 可以查看负责的 Agent、最近进展、修改文件、产物和验证情况；
- 状态来自运行事实和持久投影，不由 UI 自己猜测；
- 简单任务仍保持轻量，不出现项目控制面。

## S4：用户干预项目

**输入**：项目执行中，用户补充要求、改变方向或回答 Agent 问题。

**期望**：

- 追加背景不会被错误地当成全新无关任务；
- 尚未开始的工作项可以被修改或取消；
- 等待用户的问题明确显示等待原因和影响范围；
- 用户的决定进入项目事件和后续 Agent 上下文；
- 已经完成的结果不会因为一次追加要求被伪装成未发生。

## S5：暂停、恢复、停止和重试

**输入**：用户暂停项目、恢复项目、停止项目或重试失败工作项。

**期望**：

- 暂停、停止和失败是不同状态；
- 停止项目不会显示为正常完成；
- 恢复从可恢复事实继续，不重复伪造已完成结果；
- 重试明确是原工作项的新执行，保留旧执行记录和失败原因；
- 其他不受影响的工作项状态保持准确。

## S6：验证和证据

**输入**：代码或产物执行完成。

**期望**：

- 展示实际执行过的验证命令、环境、结果和对应 revision；
- 验证结果能关联到具体验收标准和工作项；
- 文件、产物和关键结论通过事实检查，不只依赖 Agent 自述；
- 未覆盖、冲突和未确认事项明确列出；
- 验证失败时保留已完成结果，并显示阻塞范围。

## S7：运行完成但不能交付

**输入**：所有 Agent run 已结束，但缺少文件、测试失败或验收标准未覆盖。

**期望**：

- 项目显示部分完成、受阻或待处理，而不是已交付；
- 用户看到具体缺口和下一步动作；
- 可以返回修改或重新验证；
- `run completed` 不得直接映射为 `delivered`。

## S8：用户验收和交付

**输入**：项目产生代码变更、验证结果和交付说明。

**期望**：

- 用户可以查看目标、变更、diff、预览、测试证据、已知限制和未完成项；
- 用户可以接受、要求修改或暂不决定；
- 只有明确接受后才进入已交付状态；
- commit、push、发布等外部副作用遵守独立权限和确认规则；
- 交付记录能回溯到项目、工作项、run、revision 和证据。

## S9：断线、重启和继续

**输入**：项目运行中断线或应用重启。

**期望**：

- 用户回来后能看到项目目标、阶段、工作项和最后已知事实；
- 断线不被误判为用户取消；
- 可恢复和不可恢复的工作项明确区分；
- 恢复后不会把内存中的临时状态伪装成持久事实；
- 用户可以继续观察或执行允许的恢复动作。

## S10：证据可追溯

**输入**：用户质疑最终结论或某项是否完成。

**期望**：

- 可以从交付结论追到验收标准；
- 从验收标准追到验证记录、文件/产物和 revision；
- 从验证记录追到对应工作项和 Agent run；
- 对冲突证据、未确认事项和用户豁免保留说明；
- 不把运行日志、报告、产物和最终交付说明混成同一类内容。

## 场景完成标准

每个场景后续都需要补充：

- 前置状态；
- 真实事件顺序；
- 用户可见投影；
- 可执行干预；
- 最终状态；
- 证据来源；
- 未验证范围。

在没有这些证据前，只能说“设计覆盖”，不能说工程模式已经完成。
