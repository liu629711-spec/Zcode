# Agent 项目空间：当前能力与缺口

本文件按产品目标整理当前 ZCode 能力。状态含义：

- **实际验证**：已有真实运行或用户链路证据；
- **源码具备**：底层实现存在，但用户入口或完整场景未验证；
- **入口缺失**：底层有能力，产品动作尚未完整暴露；
- **未验证**：不能仅凭源码下结论；
- **当前缺口**：需要产品层补齐。

## 现有能力与工程模式的差距

| 用户需要 | 当前状态 | 缺口 |
| --- | --- | --- |
| 从 idea 建立项目 | 入口缺失 | 普通聊天、task 和 workflow 尚未统一成用户可管理的项目对象。 |
| 项目目标和范围 | 入口缺失 | 缺少持久的项目简报、范围确认和验收标准。 |
| 方案和任务计划确认 | 入口缺失 | Expert Workflow 有分析阶段，但没有统一的用户阶段门和批准记录。 |
| 项目总览 | 入口缺失 | 已有运行和任务投影，但还没有把目标、阶段、工作项、产物、验证和交付放在一个项目视图。 |
| 过程观察 | 部分具备 | 运行状态可见，但长任务的用户语言摘要、依赖、阻塞和下一步尚未统一呈现。 |
| 项目干预 | 入口缺失 | stop/resume/amend 等底层动作存在，追加要求、改工作项、单项重试和项目级控制尚未形成统一动作模型。 |
| 工作项与执行关联 | 当前缺口 | 缺少稳定关系：项目 → 工作项 → run/session → 文件改动 → 验证证据。 |
| 验收证据 | 部分具备 | 工具输出、report、artifact、critic 和测试存在，但没有统一关联到项目验收标准的记录。 |
| 交付状态 | 当前缺口 | `run completed`、Git commit、文件存在和用户接受尚未形成独立的交付判断。 |
| 失败和部分完成 | 部分具备 | 运行时有失败/停止状态，但项目层如何保留已完成工作、标记阻塞和继续处理尚未统一。 |
| 重启后项目恢复 | 未验证 | 底层 journal/replay/resume 存在，项目级总览和干预上下文仍需真实场景验证。 |

## 重要边界

工程模式应把项目层做成现有能力的组织和投影层，而不是接管执行：

```text
项目层：目标、阶段、工作项关联、用户决定、验收与交付
现有 runtime：Agent、Task、Workflow、Host、journal、Git 和通知
UI：项目观察、用户操作和临时输入
```

项目层不能从“所有任务 completed”简单推导交付状态。执行、流程、结果和交付是不同事实，必须分别记录或投影。

## 第一阶段优先缺口

1. 定义项目、阶段、工作项、验收标准和交付记录之间的关系；
2. 用用户语言呈现现有任务和 Workflow 的状态；
3. 定义范围、方案、执行和交付的确认门；
4. 把文件改动、验证命令、artifact 和结果关联到工作项；
5. 定义追加要求、暂停、恢复、停止、重试和重新规划的动作语义；
6. 用一条端到端场景证明用户可以从 idea 走到可验收结果。

在这些规则确定前，不应直接新增项目数据库、协议命令或 UI 大改造。
