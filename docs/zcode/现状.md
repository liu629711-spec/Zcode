## 1. 一句话怎么进一次回合

UI 用 `createCommandEnvelope`（`packages/ui/src/v4/commandFactory.ts:51`）组信封：`commandId`（uuid v7）、`clientId`、`sessionId`（`createSession` 时为 null）、可选 `baseRevision` / `baseLogEpoch`、`type`、`payload`、`issuedAt`。共享 schema 是 `commandEnvelopeSchema`（`packages/shared/src/zcode-protocol-v4/command.ts:320`），`parseCommandEnvelope`（同文件 `:337`）按 type 校验 payload。用户正文是 `sendText`（同文件 `:80`），`requestedDelivery` 为 `startNow | queue | guide`。

CLI 入口是 `V4Gateway.handleCommand`（`apps/zcode-cli/packages/bootstrap/src/zcode-protocol-v4/v4-gateway.ts:2360`）。注释（同文件 `:2350-2358`）写明：RPC 等的是命令终态，不是整个模型回合；`sendPrompt` 在后台起 turn。`handle` 先交给 `CommandInbox.handle`（`apps/zcode-cli/packages/bootstrap/src/zcode-protocol-v4/command-inbox.ts:117`）。

`CommandInbox`（同文件 `:107`）是进程内、按 session 的 FIFO。锁序是 key gate，再 per-session gate；session gate 持有到 settle。结果要么立刻 `ack`，要么 `execute`（同文件 `:176`）。ACK `status` 是 `accepted | rejected | stale | duplicate | noop | failed`（`packages/shared/src/zcode-protocol-v4/command.ts:433`）。注释写明 `accepted` 不承诺跨 CLI 进程存活。

这张内存表不是输入账本。账本类型在 `apps/zcode-cli/packages/contracts/src/interfaces/session-store.port.ts:851-853`：`SessionInputDelivery = "startNow" | "guide" | "queue"`，`SessionInputStatus = "admitted" | "promoted" | "cancelled" | "discarded" | "failed"`。

Prompt 准入的所有者是该 session 的 `AgentRuntime`，入口 `admitPrompt`（`apps/zcode-cli/packages/core/src/runtime/methods/prompt-admission.ts:20`）。busy 且 `requireIdle` 或带 `modelExecution` 时拒绝。busy、当前 turn `steerable`、无附件时可以 steer；否则 `enqueueDeferredInput`，delivery 为 `guide` 或 `queue`。空闲时 `reserveTurnStart`，再入队一条 `mode: "prompt"` 的 runtime command。

回合循环不在准入里跑。`executeTurn`（`apps/zcode-cli/packages/core/src/runtime/methods/turn.ts:70`）只入队；`executeTurnCommand`（同文件 `:93`）才冻结选择并跑。模型/工具循环是 `runRegularTurnLoop`（`apps/zcode-cli/packages/core/src/runtime/methods/turn-loop.ts:43`）。

前台执行域是一条 runtime command，不是整个 session。`beginForegroundExecution`（`apps/zcode-cli/packages/core/src/runtime/methods/runtime-command-queue.ts:396`）建 `AbortController`，`foregroundExecutionId = String(command.id)`，挂到 `this.activeForegroundExecution`。`stopActiveForegroundExecution`（同文件 `:446`）返回 `stopped | idle | mismatch`。`stop` 命令可带 `expectedForegroundExecutionId`（`packages/shared/src/zcode-protocol-v4/command.ts:141`）。

当前源码没有「一句话建一个临时团队、对话继续可用、按依赖派下一个工人」这条运行时路径。一句话进入的是上述这一次回合。

## 2. 现在怎么派一个子 agent

工具名是 `Agent`（`agentToolEntry.metadata.name`，`apps/zcode-cli/packages/core/src/tool/handlers/agent.ts:227`）。别名 `Task` 在 `apps/zcode-cli/packages/core/src/tool/compat.ts:2`，`isSubagentDispatchToolName`（同文件 `:12`）把两者都当派发工具。

handler 调 `context.subagentPort.launch`（`agent.ts:211`），`runInBackground` 取自 `parsed.run_in_background === true`。端口是 `SubagentPort`（`apps/zcode-cli/packages/contracts/src/interfaces/subagent.port.ts:36` 起有 `launch` 请求形状）。实现是 `createExploreSubagentPort`（`apps/zcode-cli/packages/core/src/subagent/runner.ts:131`）。

子运行时是独立会话。`childSessionId = createSessionId(\`subagent_${agentId}\`)`（`runner.ts:806`）。`new AgentRuntime(request.sessionId, …)`（`apps/zcode-cli/packages/core/src/runtime/methods/subagent.ts:239`），`taskType: "subagent_child"`（同文件 `:271`）。`subagents.enabled: false`（同文件 `:284-287`），子运行时不能再派子 agent。

工具面：`resolveAllowedTools`（`runner.ts:2124`）对内建 Explore 用 `getAllowedTools`，否则用 `profile.tools`，再过 `filterSubagentChildToolNames`。`resolveSubagentToolAllowlist`（`subagent.ts:490`）：allowlist 空或含 `*` 时继承父可见工具，去掉派发工具名和 disallow；显式 allowlist 不与父列表求交。`filterSubagentChildToolNames`（`apps/zcode-cli/packages/core/src/subagent/tool-policy.ts:15`）一律去掉 `EnterPlanMode` 和 `ExitPlanMode`。子 runtime 还装 `coordinatorResponsePort`（`subagent.ts:308`），对应 `RespondToCoordinator`。

前台完成：`port.run`（`runner.ts:173`）await `runAgentToCompletion`，返回 `status: "completed"`（`AgentCompletedOutput`，`apps/zcode-cli/packages/contracts/src/tools/agent.ts:44`）。这次 await 堵住父工具调用，结果作为 Agent 工具结果回到父回合。

## 3. `runInBackground` 与父队列

`launch`（`runner.ts:147-170`）里，后台条件是 `rawRequest.runInBackground === true` **或** `profile.background === true`。为真时走 `port.start`，不走 `port.run`。若 `launchOptions.modelOverride.background === "deny"`，抛 `AgentErrorCode.BACKGROUND_UNAVAILABLE`，文案是 “Idle-time tasks do not support background agents”。

`start`（`runner.ts:439`）把任务登记为 `isBackgrounded: true`，`void runBackgroundAgent(...)` 不等完成。它只等 `readyGate`（会话就绪并发出 `SubagentSpawned`，同文件 `:508-509`），然后返回 `AgentBackgroundedOutput`。父工具调用在 ready 之后返回，子运行时继续跑。

另一条、不是这个 flag：`port.run` 在没有 foreground model override、且 `autoBackgroundMs` 为有限正数时，用 `createAutoBackgroundTimer` 和完成竞速（`runner.ts:291-329`）。胜者是 `backgrounded` 时 `detachParent`，返回后台输出，子继续跑。`normalizeAutoBackgroundMs`（`runner.ts:653`）对缺省、非数字、非有限、`<= 0` 返回 `undefined`，此时不装这个计时器。值来自 `this.config.subagents?.autoBackgroundMs`（`subagent.ts:70`）。配置构造时的默认值见文末未核实。

跑完叫醒父队列：`enqueueParentTaskNotification`（`subagent.ts:79`）调用 `enqueueBackgroundTaskNotification`（`apps/zcode-cli/packages/core/src/runtime/methods/background-notifications.ts:10`）。它入队一条 runtime command：`mode: "task-notification"`，`priority: "next"`，`source: "background_task"`。同时尝试 `saveSessionInput`，`kind: "backgroundNotification"`，`delivery: "queue"`。同文件 `:58-60` 写明：runtime 命令队列是纯内存的；崩溃后子进程已死，resume 把残留 `admitted` 收成 `discarded(session_resumed)`，通知不可恢复。

父回合还在循环里、且 `modelStepCount > 0` 时，`runRegularTurnLoop`（`turn-loop.ts:55-60`）调用 `drainPendingRuntimeCommandsForActiveLoop`（`apps/zcode-cli/packages/core/src/runtime/methods/runtime-command-active-loop.ts:22`）。该 drain 只吃 `task-notification` 和 `subagent-message`，遇到 `control-only-turn` 就停。父回合空闲时，`runTaskNotificationBatch`（`runtime-command-queue.ts:317`）把通知批当作新的前台执行跑起来。

所以：显式后台或 profile 后台在会话就绪后不堵住父工具调用；完成是重新进入**同一个父 runtime 命令队列**。当前源码没有另一套团队调度器来接这个完成。

## 4. 提问和权限怎么挂起、怎么回 UI

`AskUserQuestion` 的 handler 自己不等待。等待在 broker。协议侧 `createProtocolInteractionBroker`（`apps/zcode-cli/packages/bootstrap/src/zcode-protocol/interaction-broker.ts:43`）：工具名是 AskUserQuestion 走 `requestUserInput`，是 ExitPlanMode 走 `requestExitPlanModeApproval`，其余走 `requestPermission`。重发间隔常量是 1000ms（同文件 `:41`）。

两条应答汇合在 `V4InteractionRegistry`（`apps/zcode-cli/packages/bootstrap/src/zcode-protocol-v4/interaction-registry.ts:1-16` 的文件头，类在 `:90`）。旧客户端用反向 RPC；v4 客户端发前向命令 `resolveInteraction`（`packages/shared/src/zcode-protocol-v4/command.ts:173`）。先到先得，晚到 `noop`（`reasonCode=proto.alreadyResolved`）。AskUserQuestion 的自动收口时钟：隐藏宽限 60s、截止 300s（`interaction-registry.ts:30-31`）。登记表在 `server.ts:262` 按进程 `new` 出来，是进程内存。

子 agent 的 permission / AskUserQuestion / ExitPlanMode 由 `createSubagentInteractionBroker`（`apps/zcode-cli/packages/core/src/runtime/helpers/subagent-interaction-broker.ts:16`）改写到父 `sessionId`；`origin` 保留真正发起的子代理。UI 看到的是父会话上的交互，不是子会话自己的一张卡。

跨进程：同一 CLI 进程里的多个客户端可以抢答 `resolveInteraction`。进程重启后，这些 deferred 不在磁盘上。当前源码没有把挂起中的 permission/question promise 从 `session_entry` 或事件里重新注册回登记表。`runtime/user_input_auto_resolution` 只是自动收口时钟的事实，不是那份等待。冷投影会不会仍把未解决的 `PermissionRequested` 画成待处理卡，见文末未核实。

## 5. 「工人举手、队长裁决」

有一条阻塞通道，只服务动态工作流的 actor 子会话。

工具名 `escalate`（`ESCALATE_TOOL_NAME`，`apps/zcode-cli/packages/contracts/src/tools/escalate.ts:14`）。端口 `WorkflowEscalatePort.escalate`（`apps/zcode-cli/packages/contracts/src/interfaces/workflow-escalate.port.ts:58`）阻塞直到主代理作答。结局 `answered | refused`（`budget_exhausted | no_active_ask`）都是普通工具结果，不是抛错（同文件 `:28-45`）。注册门是注入了 `workflowEscalatePort`（`apps/zcode-cli/packages/bootstrap/src/app/script-workflow-child-runtime.ts:84-87`）；注释写明这是 actor 遇到真阻塞时唯一的求助通道。主代理用 `ResolveWorkflowQuestion`（`apps/zcode-cli/packages/core/src/tool/handlers/resolve-workflow-question.ts:1`）回答；handler 把 qid 和答案交给 `dynamicWorkflowRunPort.resolveQuestion`。run 继续，只有这个 actor 停在这次调用上。

它不服务普通 `Agent` 子代理。普通子代理的 `RespondToCoordinator`（`apps/zcode-cli/packages/core/src/tool/handlers/respond-to-coordinator.ts:27`）要求 `runtimeScope === "subagent"` 且有 `coordinatorResponsePort`。`createCoordinatorResponsePort`（`apps/zcode-cli/packages/core/src/subagent/coordinator-response.ts:19`）同步 `enqueue` 一条消息给父 runtime，工具立刻返回 “Response was queued for the coordinator.”。这是回复/进度入队，不是阻塞裁决。子代理的 AskUserQuestion 走到第 4 节的用户 UI，不是走到父模型当队长。

当前源码没有一条与 workflow 无关的「工人向队长举手并停住等裁决」通道。

## 6. 会话事实怎么落盘，两条出站链路

已落库事件的发布点是 `appendEvent`（`apps/zcode-cli/packages/core/src/runtime/methods/events.ts:81`）。注释（同文件 `:86-88`）写明只发布 eventStore 补号后的事件，live、replay、snapshot 的 `eventSeq` 都来自同一个 event store。正文权威是这份事件，不是 `session_entry`。

`SESSION_ENTRY_TYPES`（`apps/zcode-cli/packages/contracts/src/interfaces/session-store.port.ts:812-820`）声明的类型是：

- `target_completion_verification`
- `runtime/bash_shell_selection`
- `runtime/model_selection`
- `runtime/execution_state`
- `runtime/user_input_auto_resolution`
- `runtime/workspace_checkpoint`
- `runtime/workspace_file_rewind`

`SessionEntryInfo.type` 同时标成 `SessionEntryType | string`（同文件 `:827`），列上可以出现这张表以外的字符串。这 7 个是当前声明集合。

桌面实时：持久事件经 `v4-bridge.ts` 的 `onPersistedEvent`（`apps/zcode-cli/packages/bootstrap/src/zcode-protocol/v4-bridge.ts:1059`）进 `v4Gateway.ingest`（`v4-gateway.ts:741`）。订阅时 `subscribeReserved`（同文件 `:1364`）只认 host 注入的 `clientMode`：`desktop-continuous` → profile `continuous`，否则 `replayable`（同文件 `:1395-1397`）。桌面 host 把 `clientMode` 设为 `"desktop-continuous"`（`packages/desktop/src/host/index.ts:649`，同文件 `:936`、`:2893`）。`rowsRange` 的行可见性用同一档（`v4-gateway.ts:1567-1568`）。

手机可回放：`getTaskSnapshot`（`packages/services/src/zcode-agent/zcodeTaskServiceAdapter.ts:2459`）在 `clientMode === "web-remote-replayable"` 时回填 resume 模型提示，并 `includeEmptyPendingElicitations`（同文件 `:2464-2487`）。它调用 `resumeTaskSnapshot` → `resumeSnapshot`（同文件 `:1140`）→ `zcodeAgentService.resumeSession`。CLI 侧 `resumeSession`（`apps/zcode-cli/packages/bootstrap/src/zcode-protocol/server-operations.ts:1518`）读持久化会话，`snapshot`（同文件 `:3487`）拼出 `ZCodeSessionStateSnapshot`。手机拿到的是变换后的 task snapshot，不是 v4 帧本身。

两条都是同一份持久化会话/事件的出站档位。当前源码没有第二份可写的「团队状态」。

## 7. 已保存工作流的调度器

启动命令的 ACK 形状在 `command.ts:402-407`（`type: "startSavedWorkflow"`，带 `runId` 与 `toolCallId`）。运行时入口是 `startSavedWorkflowRun`（`apps/zcode-cli/packages/core/src/runtime/methods/dynamic-workflow-run-start.ts:62`）。文件头（同文件 `:50-57`）写明：它是 `port.submit` 的第二个调用方，与 CreateWorkflow 工具共用同一段 saved 归一化和同一个后台追踪器；不经过 `ToolExecutor.execute`。`hasActiveOrQueuedTurnWork()` 时返回 `session_busy`（同文件 `:75-77`）。

这次 run 里负责 ask 的是 `AskScheduler`（`apps/zcode-cli/packages/dynamic-workflow/src/engine/scheduler.ts:38`）。文件头（同文件 `:1-8`）写明：它只负责 ask 生命周期，不管 run 生命周期。对象是一次脚本 run 里的 ask：每 actor FIFO、`actorSeq` 准入、hold/replay、并发上限。`admitAsk`（同文件 `:103`）按 journal 节点命中短路或 live 派发；`admitLive`（同文件 `:149`）把一个 ask 建成 live 节点。journal 节点 kind 是 ask。它不调度「多个 agent 互相编排」。

另一份调度器不要并进上面这条。`WorkflowGraphScheduler`（`apps/zcode-cli/packages/core/src/workflow/scheduler.ts:34`）的 `run`（同文件 `:51`）按图上可执行节点推进，调用处是 `runScheduledPhase`（`apps/zcode-cli/packages/core/src/workflow/expert/scheduled-phase.ts:27`）。它调度的是 expert workflow 图的可执行节点，不是已保存脚本工作流的 ask。

## 8. 回合终态

`TurnResultType`（`apps/zcode-cli/packages/contracts/src/events/session.events.ts:600-607`，`apps/zcode-cli/packages/core/src/agent/turn-state.ts` 有同名联合）是：

- `success`
- `cancelled`
- `error_max_turns`
- `error_max_budget`
- `error_during_execution`
- `error_max_tool_calls`

当前写出点：常规完成发 `TurnComplete`，`resultType: "success"`（`apps/zcode-cli/packages/core/src/runtime/methods/turn.ts:386` 与 `:656`）。`appendTurnOutcomeEvent`（`apps/zcode-cli/packages/core/src/runtime/helpers/turn-errors.ts:143`）在 `TurnCancelled` 时发 `TurnComplete` 且 `resultType: "cancelled"`（同文件 `:175`），其余发 `TurnError`。`TurnError` 是另一种事件，不是上面那些 `error_*` 的 `resultType`。

`error_max_turns`、`error_max_budget`、`error_max_tool_calls` 出现在类型联合里。本次检索没有看到对这三个字面量的赋值。`error_during_execution` 出现在 transcript hydration 的类型与映射里，不是 `runRegularTurnLoop` 的终态赋值。细节见文末未核实。

「节点关没关 / 流怎么收口 / 产出好不好」三层分开的回合终态：当前源码没有。

旁边、但是别的词汇：

- 工作流节点 `NodeOutcome = "ok" | "failed" | "cancelled"`（`apps/zcode-cli/packages/dynamic-workflow/src/engine/types.ts:578`）。
- run `RunStatus = pending | running | completed | errored | stopped`（同文件 `:589`），停下原因 `RunStopReason`（同文件 `:597`）。这是一次动态工作流 run 的生命周期，不是回合终态。
- 目标验证 `TargetCompletionVerificationStatus = started | completed | failed_closed | cancelled`（`session.events.ts:647-651`），落在 `session_entry` 类型 `target_completion_verification`。这是目标事实，不是回合终态的第三层，也不是工人交付物的核验档。
